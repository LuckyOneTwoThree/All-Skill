# 上线复盘指挥官

## 核心原则

**发布不是终点而是学习的起点**

每一次发布都是一次实验，复盘是将实验结果转化为组织知识的过程。没有复盘的发布是浪费，没有行动的复盘是形式。

## 执行步骤

1. **触发器驱动**：全量发布完成自动触发复盘计划，T+2周自动触发效果复盘
2. **自动化验收**：多源数据自动收集，效果对比自动生成，行动项自动追踪闭环
3. **持续部署**：复盘行动项直接反馈到开发协作流程，形成持续改进闭环
4. **实时复盘**：发布后快速复盘即时启动，效果复盘T+2周自动触发，避免信息衰减

## 任务调度

```
retrospective-auto
```

### 调度逻辑

| 触发事件 | 调度动作 |
|----------|----------|
| 全量发布完成 | → retrospective-auto（启动复盘计划） |
| T+2周时间点 | → retrospective-auto（执行效果复盘） |
| T+4周时间点 | → retrospective-auto（最终复盘确认） |
| 效果严重偏离 | → retrospective-auto（触发深度分析） |

### 数据流转

```
[发布完成事件]
       ↓
retrospective-auto
       ↓ retrospective_report / action_items / closure_report
       ↓ (行动项反馈)
[开发协作编排器] / [质量保障编排器]
```

## 调度规则

- 每次只加载当前阶段需要的子Skill，完成后再加载下一阶段，不要一次性加载所有子Skill
- 每个阶段完成后，将中间结果写入 `output/pm-development/{skill-name}/` 文件，释放上下文空间
- 若上下文接近上限，优先保留当前阶段内容，将已完成阶段的输出摘要为关键结论
- 单个子Skill的输出应控制在2000字以内，超出部分写入文件

## 阶段卡口

| 卡口 | 通过条件 | 未通过处理 |
|------|----------|------------|
| 效果数据T+2周已收集 | 监控数据、用户反馈、团队反馈已汇总 | 延长收集时间或补充访谈 |
| 行动项有负责人 | 每个行动项都有明确负责人和截止时间 | 标记为open，持续追踪 |

## 人类决策点

| 决策点 | 触发条件 | 决策内容 |
|--------|----------|----------|
| 复盘结论确认 | 复盘报告生成完成 | 确认复盘结论的正确性和行动项的合理性 |

## 异常处理

| 异常类型 | 处理策略 |
|----------|----------|
| 数据源不可用 | 使用历史数据或标记数据缺失 |
| 团队反馈率低 | 延长收集时间或进行访谈补充 |
| 行动项无法完成 | 重新评估优先级或延期 |
| 复盘结论争议 | 组织专项讨论会议 |
